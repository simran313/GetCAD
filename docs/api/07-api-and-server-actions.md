# API and Server Action documentation

The CAD Pillar has no public, third-party API. Its server interface has three parts:

- **Server Actions**, which the portal's forms call;
- **Route handlers** under `/api`, for downloads, documents, polling, health, scheduled jobs and the payment webhook;
- **Database functions**, which the server calls through Supabase's Data API (PostgREST) on behalf of the signed-in person.

This chapter documents each part, its contract and its security. The generated inventories are [Appendix C](./generated/routes.md) (routes) and [Appendix D](./generated/server-actions.md) (actions).

## Conventions

| Convention | Rule |
|---|---|
| Authentication | Every non-public handler and action starts with Clerk `auth()`. With no user it returns `401 unauthenticated` (handlers) or throws `Refusal` (actions). |
| Authorisation | Decided by the database: a SECURITY DEFINER function or an RLS-filtered read through the user-scoped client. Handlers answer `404 not found` for both "doesn't exist" and "not yours", so ids cannot be probed. |
| Caching | Personal responses send `Cache-Control: no-store`. |
| Downloads | Never stream from a public URL. Authorise, then redirect to a Supabase signed URL valid for **60 seconds** (`SIGNED_URL_TTL_SECONDS`). The STL stream endpoint proxies bytes through the same gate. |
| Errors | Friendly text for people (`lib/refusal.ts`, `core/errors`). Database messages are mapped, never shown raw to clients. |
| Idempotency | Payment and payout operations carry idempotency keys (`razorpay:payment.captured:<id>`, payout keys), so retries are safe. |
| Cross-site requests | Server Actions get Next.js's Origin check. `POST /api/threads/[id]/read` refuses `sec-fetch-site: cross-site`. |

| `POST /api/webhooks/razorpay` | Payment captured or failed; transfer processed or reversed | HMAC-SHA256 of the raw body with `RAZORPAY_WEBHOOK_SECRET`, verified in constant time **before parsing** | 200 handled or ignored; 401 invalid signature; 500 to ask Razorpay to retry |

Other public endpoints: `/robots.txt`, `/sitemap.xml`, `/manifest.webmanifest` (generated by `app/robots.ts`, `app/sitemap.ts` and `app/manifest.ts`), and `/p/[token]`, the public preview page. That page hashes the token and looks it up with `preview_by_token()`, which checks expiry and revocation and counts views; tokens are 192-bit random.

### The Razorpay webhook, step by step

1. Read the **raw body** before parsing anything.
2. Verify `x-razorpay-signature` with HMAC-SHA256 and a constant-time comparison (`core/payments/razorpaySignature.ts`). If it fails, return 401 with no detail.
3. Parse the event and switch on its type.
   - `payment.captured` → `confirm_payment()` with the idempotency key `razorpay:payment.captured:<payment id>`. The ledger gets a HOLD and the order becomes paid.
   - `payment.failed` → `fail_payment_intent()`.
   - Transfer events → `record_payout_result()` with the payout key. A reversal credits escrow back.
4. On a database error, return 500 so Razorpay retries. Idempotency makes the retry harmless.
5. `/api/health` reports `payments: false` if the webhook secret is weak, is a URL, or equals the key secret.

### Scheduled endpoints

Vercel Hobby allows a cron only once a day, so `.github/workflows/push-dispatch.yml` calls `/api/cron/push` and `/api/cron/emails` every five minutes with the `CRON_SECRET` bearer token. On Vercel Pro, move the schedule back to `vercel.json` (the instructions are at the top of that workflow file). The SLA sweep (`sla_sweep()`) is separate: it runs every minute inside Postgres through `pg_cron` **if the extension is enabled** in Supabase. That is not verifiable from the code (see the assumptions chapter).

### Writing a new action: checklist

- [ ] `"use server"` at the top of the file. Export only async functions.
- [ ] `const { userId } = await auth()`, and refuse if empty.
- [ ] Use `createUserSupabaseClient()`. Use the service role only after an authorised read has proven access, and say why in a comment.
- [ ] Do the permission check in a database function: SECURITY DEFINER, `search_path` pinned, caller checked, audited.
- [ ] Validate input (zod) and cap sizes; reject unexpected fields.
- [ ] `revalidatePath` for the pages whose data changed.
- [ ] Return friendly messages; never leak database errors or identities.
- [ ] Add a test in `tests/db/` for allowed and refused callers, and an e2e step if it is a user journey.
